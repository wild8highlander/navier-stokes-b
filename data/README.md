The provenance layer of the repository: everything produced by the runs in
[`code/`](../code/README.md), preserved exactly as recorded on **2026-09-16**.
This directory is the single point of truth for every quantitative claim made
anywhere else in the repository — the root README, the papers, the monograph
and the open-problems registry all quote these files, never the other way
round. If a number in any document disagrees with a JSON here, **the JSON is
authoritative** and the document is wrong.

Two properties make this layer trustworthy. First, it is **complete**: each
protocol stores not only the headline numbers but the producing command, the
full parameter set, the pre-registered success criteria, the tolerances and
the wall-clock time, so a reader can rerun and diff rather than trust.
Second, it is **pinned**: every file's sha256 and byte size are recorded in
[`MANIFEST.json`](../MANIFEST.json), the CI job *Manifest integrity* fails on
any drift, and the plots are regenerated by
[`code/make_plots.py`](../code/README.md) *from the JSONs* — there is no path
by which an image could disagree with its data.

## Reading order

1. [`results/summary_numbers.json`](results/summary_numbers.json) — **every**
   quoted number of the program in one machine-readable file: the 50-digit
   constants of L1, the rotation-algebra residuals of L2, the Kirchhoff
   RK4-order diagnostics of L3, the 2D NSE identities of L4, the BKM
   integral of L5, and the headline values of P1–P6;
2. the per-run protocol next to it (`p1_3d_microphysics.json` …
   `p6_b_universality.json`) — commands, parameters, criteria, tolerances;
3. [`results/baseline/`](results/baseline/README.md) — the pinned verdicts
   of the L1–L5 verification chain, the regression baselines every rerun
   must land on;
4. [`plots/`](plots/README.md) — the visual form of the same numbers.

## The contract

These files are **immutable evidence**: the documentation quotes them, the
manifest pins their sha256, and CI checks that nothing drifts. Regenerating
them is allowed only as one atomic change: rerun the producing script in
[`code/`](../code/README.md), let the JSONs and plots regenerate, update the
documentation tables that quote them, and refresh
[`MANIFEST.json`](../MANIFEST.json) (`make manifest`) — all in the same
commit. Anything else breaks the chain and will be caught.

## Integrity check

```bash
make verify-manifest     # PASS/FAIL for every file in the tree
```

or point any sha256 tool at a single file and compare against
[`MANIFEST.json`](../MANIFEST.json). If you reproduce a run on your own
hardware and your JSON differs from the pinned one beyond the stated
tolerances, that is a high-priority
[verification request](https://github.com/wild8highlander/navier-stokes-b/issues/new?template=verification_request.yml)
— please include your commit hash, platform and toolchain versions.


## The integrity workflow, step by step

1. **Check** — `make verify-manifest` walks the tree, hashes every file and
   compares against [`MANIFEST.json`](../MANIFEST.json): a PASS line per
   file, a FAIL with the diff direction otherwise;
2. **Regenerate** (only after a legitimate rerun) — `cd code && ./run_all.sh`
   rewrites the protocols and plots; `make manifest` refreshes the pinned
   hashes and the manifest date;
3. **Commit atomically** — the regenerated evidence and the updated
   documentation that quotes it travel in one commit; CI re-checks both
   sides of the contract.

## Why the binary snapshots exist

`p1_positions.npz` and `p3_theta_snapshot.npy` are the raw field/trajectory
arrays behind two of the five plots. They exist so that
[`code/make_plots.py`](../code/README.md) never re-simulates to draw: the
figures are a *projection of recorded data*, which removes the entire class
of "the plot disagrees with the run" failures. They are also the fastest
way to inspect the runs without re-running them (numpy opens both in
milliseconds).

## FAQ

**Can I cite a number from a plot?** No — cite the JSON protocol (or
`summary_numbers.json`) that produced it; the plot is a rendering.

**The documentation and a JSON disagree — who wins?** The JSON, always.
Open a
[verification request](https://github.com/wild8highlander/navier-stokes-b/issues/new?template=verification_request.yml)
and the document gets fixed.

**Can I add my own run outputs here?** Not to the pinned files. Add a new
`p*_variant.json` alongside, with the same envelope schema, and describe it
in the same change — the manifest and this README must move together.

**Why 2026-09-16 everywhere?** That is the date the recorded program was
executed and the repository was assembled from
[`wild8highlander/research-papers`](https://github.com/wild8highlander/research-papers);
the protocols freeze that session.
